## R-1. 배포를 003 에 포함할 것인가

**결정**: 포함하지 않는다. **001 의 Phase 6(T039–T046)을 먼저 끝내 정적 사이트를 띄운 뒤**
003 을 그 위에 얹는다. 003 은 API 컨테이너와 데이터베이스, 그리고 방명록 화면만 다룬다.

**근거**: 위험을 분리한다. DNS·인증서·인그레스·CI 는 처음 세울 때 반드시 한 번은 막히는
자리인데, 그 문제를 새 DB 롤과 판정 API 연동과 함께 겪으면 원인 범위가 두 배가 된다.
정적 사이트가 도메인에 뜬 것을 확인하고 나면, 003 에서 새로 생기는 변수는 API 하나뿐이다.

배포 산출물은 같은 `deploy/` 트리를 쓰므로 두 번 만드는 일은 없다. 001 이 `50-web.yaml`
까지 만들고, 003 이 `60-api.yaml` 을 더한다.

**기각**: 003 에 전부 포함 — 한 번에 끝나 보이지만, 첫 배포가 실패했을 때 방명록 코드와
인프라 중 어디가 문제인지 가려내는 비용이 더 크다.

## R-2. 방명록 책은 3D 리더로 열지 않는다 — **뒤집힘 (2026-08-01)**

> **이 결정은 뒤집혔다. 방명록도 3D 로 연다.** 아래 원문은 기록으로 남긴다.
>
> **왜 틀렸나.** 근거 두 가지 중 **2번(글꼴)이 사실이 아니었다.** 서브셋 글꼴은 HTML 이
> 어떤 글꼴을 쓸지 정할 뿐이고, 캔버스에 그리는 글자는 `ctx.font` 로 아무 글꼴이나
> 지정할 수 있다. 방문자 글만 시스템 글꼴 스택으로 그리면(HTML 쪽 `.guestbook__body`
> 와 똑같은 처리다 — R-3) 무슨 글자가 와도 그려진다. 없는 제약을 있다고 본 것이다.
>
> 1번(입력칸)은 사실이지만 3D 를 막지는 않는다. **3D 가 한 면을 통째로 비우고, 그 면의
> 화면 좌표에 진짜 `<form>` 을 얹으면 된다.** z=0 평면이 화면 픽셀과 1:1 로 대응하도록
> 카메라를 잡아 두었으므로 자리는 계산으로 나온다. 얹힌 것은 평범한 HTML 이라 IME·
> 붙여넣기·포커스·낭독기가 모두 그대로 동작한다 — 원문이 걱정한 접근성 위험은 캔버스
> 안에 입력을 흉내낼 때의 이야기였고, 여기서는 흉내내지 않는다.
>
> **바뀐 것**: `about-guestbook.md` 의 `reader: flat` 제거, `Block` 에 `entry`·`writebox`
> 추가, `Book3D.writeboxRect()`, `BookController.placeWriteBox()`,
> `guestbook.css` 의 `[data-on-page]`. 평면 마크업은 지우지 않았다 — WebGL 이 없는
> 환경의 폴백이자 낭독기·검색이 읽는 본문으로 그대로 남는다.
>
> **함께 알게 된 것**: 폼을 `.book__pages` 밖으로 옮겨야 3D 위에 얹을 수 있는데
> (`opacity:0` 은 쌓임 맥락을 만들어 자식이 벗어날 수 없다), 그러면 책이 다 펼쳐질
> 때까지 폼이 문서 흐름에 남아 화면이 크게 튄다(CLS 0.175, 예산 0.1). 그래서 접는 기준을
> `data-reader` 가 아니라 창을 여는 순간 붙는 `data-open3d` 로 잡았다(0.015 — 다른 책과
> 같은 값).

**결정**(원문): 방명록 책만 **평면 모달**로 연다. 나머지 책은 지금처럼 3D 리더로 연다.
`BookController` 가 책마다 리더 방식을 고를 수 있게 하고, 방명록 책은 3D 를 켜지 않는다.

**근거**: 두 가지가 모두 3D 를 막는다.

1. **캔버스 안에는 입력칸을 놓을 수 없다.** 3D 리더는 페이지를 WebGL 텍스처로 그린다.
   그 위에 글자를 입력받을 방법이 없다. 지금도 조작 버튼은 HTML 을 재사용해 캔버스 위에
   얹는데, 여러 줄 입력·포커스·IME(한글 조합)까지 그렇게 얹는 것은 접근성 위험이 크다.
2. **글꼴이 없다.** 이 사이트는 콘텐츠에 실제로 쓰인 글자만 담은 서브셋 글꼴을 쓴다
   (`scripts/subset-fonts.mjs`). 방문자가 무슨 글자를 쓸지는 빌드 시점에 알 수 없다.
   스크립트 주석에도 이미 적혀 있다 — "방명록(003)은 방문자가 어떤 글자를 쓸지 미리 알 수
   없어 이 방식이 통하지 않는다."

평면 모달로 열면 둘 다 사라진다. 입력은 평범한 `<textarea>` 이고, 글꼴은 브라우저가
`unicode-range` 로 필요한 구간만 받거나 시스템 글꼴로 떨어진다(R-3).

**기각**:
- 3D 로 읽고 폼만 캔버스 밖에 — 읽기와 쓰기가 다른 표면에 있어 흐름이 끊기고, 글꼴 문제는
  그대로 남는다.
- 방문자 글자를 미리 받아 서브셋에 넣기 — 불가능하다. 빌드 시점에 존재하지 않는 글이다.

## R-3. 방명록 글의 글꼴

**결정**: 방명록 화면에 한해 본문 글꼴을 **시스템 글꼴 스택**으로 둔다. 방문자가 남긴 글과
입력칸 모두 해당한다. 3D 로 그리는 글(`Block` 의 `entry`)도 같다 — 캔버스에서도 `ctx.font`
에 같은 스택을 준다. 이 결정은 그대로 유효하며, R-2 를 뒤집은 근거이기도 하다. 방명록 화면의 사이트 자체 문구(제목·안내·버튼)는 기존 서브셋 글꼴을
그대로 쓴다 — 그 글자들은 빌드 시점에 안다.

**근거**: 서브셋에 없는 글자는 빈 네모로 뜬다. 방문자 글은 정의상 예측할 수 없다. 시스템
글꼴은 한 바이트도 더 받지 않고 모든 글자를 렌더한다. 원칙 III(글꼴은 self-host·subset)의
취지는 웹폰트를 무겁게 받지 말라는 것이므로, 웹폰트를 아예 쓰지 않는 이 선택은 그 취지에
어긋나지 않는다.

**기각**: 유니코드 구간 분할 글꼴을 방명록에만 추가 — 001 research 가 대안으로 남겨 둔
방식이다. 브라우저가 필요한 구간만 받지만, 한글은 구간 하나가 수백 KB 라 글 몇 줄 때문에
그만큼을 받는다. 서브셋 방식(두 굵기 219KB)으로 사이트 전체를 커버하는 지금 구성에
방명록 하나 때문에 두 배 이상을 얹을 이유가 없다.

## R-4. API 런타임

**결정**: **Node.js 22 LTS + Fastify 5 + TypeScript**. 컨테이너는 `node:22-alpine` 기반
멀티스테이지 빌드.

**근거**: 필요한 것이 라우팅·본문 검증·레이트리밋·CORS 넷인데 Fastify 는 이 넷을 다 갖고
있다. JSON Schema 검증이 내장이라 요청 검증을 직접 짜지 않아도 되고(FR-002), 그 스키마가
그대로 계약 문서가 된다. 상주 메모리는 60~90MB 수준으로, oneBite 백엔드(JVM)와 같은 노드에
올려도 부담이 적다. 기동은 1초 안쪽이라 oneBite 가 겪은 startupProbe 90초 문제가 없다.

**기각**:
- Spring Boot — 가장 익숙하고 배포 라인도 같지만, JVM 400~600MB 와 기동 90초는 방명록
  하나에 치를 값이 아니다. 이미 파이 3노드에 oneBite 백엔드·Kafka·Postgres·n8n·Loki·
  Grafana 가 올라가 있다.
- 순수 `node:http` — 의존성 0 이 매력적이지만 검증·레이트리밋을 직접 짜야 하고, 그 코드가
  바로 원칙 IV 의 "REQUIRED 테스트 대상"이 된다. 검증된 플러그인을 쓰는 편이 낫다.
- Hono — 더 가볍지만 레이트리밋·검증 생태계가 얇아 결국 직접 짜게 된다.

## R-5. 데이터베이스 접근과 스키마 관리

**결정**: 드라이버는 `pg`(node-postgres)를 직접 쓴다. ORM 을 두지 않는다. 스키마는
`migrations/` 아래 번호를 붙인 순수 SQL 파일로 두고, 기동 시 `schema_migrations` 테이블을
보고 적용되지 않은 것만 실행하는 40줄짜리 러너를 만든다.

**근거**: 테이블이 둘이다. ORM 의 이득(관계 탐색·타입 생성)이 나올 규모가 아니고, 방명록
쿼리는 목록 조회와 삽입이 전부다. 순수 SQL 이 무슨 일이 벌어지는지 가장 분명하다.
러너를 두는 이유는 나중에 컬럼을 하나 더할 때 `CREATE TABLE IF NOT EXISTS` 로는 대응이
안 되기 때문이다.

**기각**:
- Prisma — arm64 에서 엔진 바이너리를 챙겨야 하고 이미지가 커진다.
- Drizzle — 가볍고 좋지만 테이블 둘에 스키마 DSL 을 배우게 할 이유가 없다.
- `CREATE TABLE IF NOT EXISTS` 만 — 첫 배포는 되지만 두 번째 변경에서 막힌다.

oneBite 는 Flyway 를 쓰지만 그것은 JVM 도구다. 같은 역할을 Node 쪽에서 최소로 흉내 낸다.

## R-6. 공유 PostgreSQL 에 계정 분리하기

**결정**: `onebite` 네임스페이스에 떠 있는 PostgreSQL 인스턴스에 **portfolio 롤과 portfolio
데이터베이스를 수동으로 한 번** 만든다. 접속 주소는
`postgres.onebite.svc.cluster.local:5432`. 비밀번호는 portfolio 네임스페이스의 Secret 에 둔다.

```sql
CREATE ROLE portfolio LOGIN PASSWORD '<생성한 값>';
CREATE DATABASE portfolio OWNER portfolio;
REVOKE ALL ON DATABASE portfolio FROM PUBLIC;
```

**근거**: oneBite 의 `20-postgres.yaml` 은 앱 롤을 `/docker-entrypoint-initdb.d` 의 스크립트로
만든다. 그 디렉터리의 스크립트는 **데이터 디렉터리가 빈 최초 기동에서만** 실행된다. 이미
데이터가 있으므로 ConfigMap 에 portfolio 롤 생성을 추가해도 아무 일도 일어나지 않는다.
돌고 있는 인스턴스에 직접 붙어 만드는 것 외에 방법이 없다.

데이터베이스를 나누면 portfolio 롤이 onebite 데이터에 닿지 못한다. 같은 데이터베이스에
스키마만 나누는 것보다 격리가 확실하다.

**주의할 것**: 이 작업은 매니페스트에 남지 않는 수동 절차다. 절차를 `quickstart.md` 에
적어 두고, 클러스터를 다시 세울 때 잊지 않도록 `deploy/k8s/` 에 주석으로도 남긴다.

**기각**:
- portfolio 전용 PostgreSQL 을 따로 띄우기 — 격리는 가장 확실하지만 파이에 인스턴스를 하나
  더 올린다. 방명록 한 테이블에 그럴 이유가 없다.
- onebite 롤을 그대로 쓰기 — 사용자가 명시적으로 분리를 요구했고, 옳은 요구다.

## R-7. 유해성 판정

**결정**: **Claude API**. 글이 들어오면 이름과 내용을 보내 `공개 / 보류 / 차단` 중 하나와
사유를 받는다. 응답은 구조화된 형태로 강제한다. 실패·시간 초과는 **보류**로 떨어뜨린다
(FR-013). API 키는 Secret 에 둔다.

**근거**: 처음에는 Google Perspective API 로 정했으나 조사 중에 **2026년 12월 31일 종료**가
확인됐다. 연장도, 마이그레이션 도구도, 대체 서비스 안내도 없다. 다섯 달 쓰자고 같은 작업을
두 번 할 이유가 없다.

Claude 는 종료 예고가 없고, oneBite 에서 이미 쓰는 것과 같은 라인이다. 무엇보다 욕설 점수
하나가 아니라 "광고 같은데 교묘한 글", "사람을 특정해 비방하는 글"처럼 규칙으로 못 잡는
것을 맥락으로 판단한다. 방명록 한 건에 드는 비용은 사실상 0 이다.

**확인한 사실**: Perspective 의 디스커버리 문서에서 `AnalyzeCommentRequest.doNotStore` 의
기본값이 false 였다 — 명시하지 않으면 제3자가 방문자 글을 저장할 수 있다. 어떤 판정
서비스를 쓰든 이 성격의 옵션을 확인해야 한다는 교훈으로 남긴다.

**기각**:
- Perspective API — 위 사유.
- 금칙어 사전만 — `ㅅㅂ`·`씨1발` 같은 변형에 뚫리고 사전을 계속 관리해야 한다. 다만 2층
  규칙은 어차피 두므로, 판정이 없어도 광고성 글은 상당수 걸린다.

## R-8. 방문자 글의 정화 범위

**결정**: 방명록 글에 **마크다운도 HTML 도 허용하지 않는다.** 순수 텍스트로 저장하고, 줄바꿈만
살려서 보여준다. 화면에는 `textContent` 로 넣는다.

**근거**: 허용하지 않으면 정화할 것이 없다. 정화 라이브러리를 붙이는 순간 그 라이브러리의
우회 기법이 우리 위험이 된다. 방명록에 표·인용·이미지가 필요할 이유가 없다.

`src/lib/markdown.ts` 주석의 경고 — "방명록(003)이 들어오면 반드시 정화를 거쳐야 하고 이
함수를 그대로 쓰면 안 된다" — 는 이 결정으로 지켜진다. 그 함수는 방명록 경로에서 호출되지
않는다.

링크도 자동으로 걸지 않는다. 주소를 적어도 글자로만 보인다. 스팸의 동기 자체를 줄인다.

**기각**: 제한된 마크다운(굵게·기울임)만 허용 — 표현은 늘지만 정화 코드와 그 테스트가
생긴다. 방명록에 굵은 글씨가 필요하지 않다.

## R-9. 주인 인증

**결정**: 길고 무작위한 **관리 토큰 하나**를 Secret 에 두고, 보류함 조회·공개·삭제 요청의
`Authorization` 헤더로 확인한다. 관리 화면은 사이트의 정적 페이지 하나(`/admin`)로 두고,
주인이 토큰을 붙여 넣으면 브라우저에 보관한다.

**근거**: 사용자가 한 명이다. 계정 테이블·비밀번호 해시·세션·재발급을 만드는 순간 지켜야 할
것이 늘어나는데, 지키는 대상은 여전히 한 사람이다. 토큰 하나면 충분하고, 유출되면 Secret 을
바꿔 회전한다.

**기각**:
- GitHub OAuth — 본인 확인은 확실하지만 방명록 하나에 OAuth 왕복을 붙이는 것은 과하다.
- 인그레스 Basic 인증 — 간단하지만 자격이 인프라 설정에 묻혀 회전이 번거롭다.

## R-10. 남용 기록을 어디에 둘 것인가

**결정**: 두 겹으로 둔다. 프로세스 안의 짧은 창(`@fastify/rate-limit`)으로 순간 폭주를 막고,
**되돌릴 수 없게 바꾼 접속 식별값**을 데이터베이스에 남겨 재시작 뒤에도 시간당 제한이
유지되게 한다. 보관 기간이 지난 기록은 주기적으로 지운다.

**근거**: 파드가 하나라 인메모리만으로도 대부분 막히지만, 배포할 때마다 카운터가 초기화된다.
공격자가 그 틈을 노릴 만큼 대단한 사이트는 아니지만, 기록을 DB 에 두는 비용이 낮다.

원문 IP 를 저장하지 않는 이유는 헌장이다 — 개인정보는 "방문자가 자발적으로 제출한 것"만
허용한다. 접속 주소는 자발적 제출이 아니다. 소금을 섞은 해시로만 남기고 짧게 보관한다
(FR-020).

**기각**: Redis — 파드가 하나인데 상태 저장소를 하나 더 띄울 이유가 없다.
