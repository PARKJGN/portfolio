# Quickstart — 검증 가이드

**Feature**: 방·책장·책 모달 골격 | **Date**: 2026-07-22

이 기능이 실제로 동작하는지 확인하는 절차다. 구현 코드가 아니라 **검증 방법**을 적는다.

| 항목 | 버전 |
|---|---|

| 패키지 매니저 | npm |

```bash

```

## 검증 1 — 성능 예산 실측 (R-1, 가장 먼저 할 것)

**이 검증이 다른 모든 작업보다 먼저다.** 결과에 따라 프레임워크 결정이나 헌장 개정이 필요할 수 있다.

```bash
npm run build
```

확인할 것:
- 빌드 출력의 **First Load JS**를 `/`에 대해 기록한다(책은 별도 라우트 없이 방 페이지에 프리렌더된다).
- Three.js 는 첫 책 클릭 때 동적 import 되므로 초기 번들에 들어가지 않는다 — 이를 함께 확인한다.
- 실제 산출물의 압축 크기를 잰다.

판정:
- **100KB 이하** → 헌장 유지. 이 수치를 Lighthouse CI 예산으로 고정한다.
- **초과** → 클라이언트 컴포넌트를 더 줄일 수 있는지 확인하고, 그래도 넘으면 **작업을 멈추고**
  실측값을 근거로 헌장 원칙 III의 MAJOR 개정 여부를 결정한다. 초과 상태로 계속 진행하지 않는다.

## 검증 2 — 내용이 서버 렌더 HTML 로 존재하는가 (원칙 I, 헌장 3.0.0)

책 읽기 조작은 JS(3D/모달)를 전제로 하지만, 내용 자체는 낭독기·검색이 읽도록 문서에 존재해야 한다.

1. `/`의 정적 산출물(`out/index.html`)을 연다 → 모든 책 본문이 `<dialog>` 안에 서버 렌더
   HTML 로 들어 있다(검색·낭독기가 읽을 수 있다).
2. 낭독기로 방을 훑는다 → 책 제목·본문이 문서 순서대로 읽힌다.

**내용이 클라이언트 스크립트 안에만 존재하면(문서에 없으면) 원칙 I 위반이다.**

## 검증 3 — 두 보기 모드 (US2, FR-007~011)

1. 책을 연다 → 기본은 "한 장씩 넘기기"다.
2. 앞뒤로 넘긴다 → 현재 위치와 전체 분량이 표시된다.
3. "전체 이어보기"로 전환한다 → **한 번의 조작**으로 바뀐다.
4. 전체 보기에서 처음부터 끝까지 훑는다 → 한 장씩 보기에서 본 내용이 빠짐없이 있다.
5. 창을 닫고 **다른 책**을 연다 → 전체 보기로 열린다 (FR-009).
6. 브라우저 창 너비를 바꾼다 → 장이 다시 나뉘지만 읽던 위치를 잃지 않는다.

## 검증 4 — 키보드만으로 (US3)

마우스를 쓰지 않고:

1. Tab으로 방을 훑는다 → 모든 책에 보이는 초점 표시와 함께 도달한다.
2. Enter로 책을 연다.
3. 계속 Tab을 누른다 → **초점이 창 밖으로 새어 나가지 않는다** (FR-013).
4. Esc를 누른다 → 창이 닫힌다 (FR-005).
5. 방금 열었던 책에 초점이 돌아와 있다 (FR-006).
6. 좁은 화면에서 Tab만으로 두 번째·세 번째 책장에 도달한다 (FR-019).

## 검증 5 — 좁은 화면 (FR-017, FR-018)

브라우저를 **320px** 폭으로 줄이고:

1. 페이지 자체에 가로 스크롤이 생기지 않는다.
2. 책장 사이를 옆으로 넘겨 이동할 수 있다.
3. 현재 몇 번째 책장인지 알 수 있다.
4. 책을 열면 본문이 읽히는 크기로 표시된다.

## 검증 6 — 움직임 최소화 (FR-016)

운영체제에서 "동작 줄이기"를 켜고:

1. 책을 연다 → 책이 튀어나오는 연출 없이 즉시 열린다.
2. 장을 넘긴다 → 넘김 연출 없이 내용만 바뀐다.

## 검증 7 — 빈 책장 (FR-014)

프로젝트·방명록 책장에 책이 없는 상태에서:

1. 비어 있음이 드러난다.
2. 눌러도 빈 창이 열리지 않는다.
3. 방문자가 고장으로 오해할 만한 표시가 없다.

## 자동 검사

```bash
npm test             # Vitest — 콘텐츠 스키마, 슬러그, 모드 상태
npm run test:e2e     # Playwright — 검증 3·4·5 자동화 + axe 접근성
npm run lint         # 임의값 클래스 금지 규칙 포함
npx lhci autorun     # 성능 예산
```

**머지 조건**: 위 네 가지가 모두 통과해야 한다. axe 위반은 0건이어야 한다.

## 콘텐츠 추가가 정말 쉬운가 (SC-007)

새 책 한 권을 추가해 본다:

```bash
# 파일 하나만 만든다
src/content/books/profile/새-책.md
```

[`contracts/content-schema.md`](./contracts/content-schema.md)의 형식대로 프론트매터와 본문을 쓰고
저장하면, 개발 서버에서 방에 바로 나타나야 한다. **다른 파일은 건드리지 않아야 한다.**
화면 구성 코드를 고쳐야 했다면 FR-015 위반이다.

### 수행 기록 (T049 · 2026-07-31)

`src/content/books/project/temp-verify.md` 한 개만 만들어 확인하고 지웠다.

| 확인한 것 | 결과 |
|---|---|
| 화면 구성 코드 변경 없이 책등이 방에 생기는가 | 예 — 프로젝트 책장에 4권 → 5권 |
| 눌러서 열리고 본문이 읽히는가 | 예 |
| Esc 로 닫히는가 | 예 |
| 정적 HTML(`out/index.html`)에 제목·본문이 들어가는가 | 예 |
| 콘솔 오류 | 없음 |
| 파일을 지우면 방에서도 사라지는가 | 예 |

**FR-015 는 지켜진다.** 화면 구성 코드는 한 줄도 건드리지 않았다.

**SC-007 의 "콘텐츠 파일 1개만 수정하면 된다"는 문자 그대로는 지켜지지 않는다.** 새 한글이
들어가면 서브셋 글꼴을 다시 만들어야 하고, 그러면 파일 셋이 더 바뀐다(woff2 둘 +
`scripts/generated-charset.txt`). 이번 검증에서도 `렀`·`왜` 두 글자가 없어 단위 테스트가
막았다.

다만 **10분 안에 끝난다는 조건은 넉넉히 지켜진다** — `npm run fonts:build` 는 4초다. 검사가
무엇을 해야 하는지 문구로 알려 주므로 헤맬 일도 없다. 고치려면 글꼴 서브셋을 빌드 시점에
만들어야 하는데, 그러면 모든 도커 빌드가 23MB 원본 글꼴을 받아야 한다(arm64 크로스빌드라
가볍지 않다). 지금은 알고 두는 쪽을 택했고, SC-007 은 "콘텐츠 파일 1개 + `fonts:build`"로
읽는다.

프론트매터를 틀리면 빌드가 어디가 왜 틀렸는지 말해 준다 — 실제로 없는 책등 색을 넣어 보니:

```text
ContentError: 책 프론트매터가 잘못됐다: project/temp-verify.md
  — spine.color: Invalid enum value. Expected 'crimson' | 'walnut' | ... , received 'moss'
```

## 배포 확인

빌드 산출물을 컨테이너로 만들어 올린 뒤:

1. `https://<도메인>`이 열린다.
2. 인증서가 유효하다 (cert-manager 자동 발급).
3. 책을 눌러 3D/모달로 열고 닫는다 — 라우트는 `/` 하나뿐이므로 새로고침해도 방으로 돌아온다.

배포 매니페스트 작성 전에 중앙 인그레스의 기존 호스트와 충돌하지 않는지 확인한다:

```bash
kubectl -n default get ingress ingress-host -o yaml
```
