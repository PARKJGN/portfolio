# Phase 0 — 연구 및 결정

**Feature**: 방·책장·책 모달 골격 | **Date**: 2026-07-22

명세와 `design-notes.md`가 계획 단계로 넘긴 미해결 사항, 그리고 기술 선택에서 파생된 과제를 정리한다.

## R-1. Next.js의 JS 용량이 100KB 예산 안에 들어오는가 *(실측 완료 — 2026-07-22)*

> ### 실측 결과: **통과. 단, 여유가 5.6KB뿐이다.**
>
> Next.js 14.2.35 · React 18.3.1 · 정적 export · 클라이언트 컴포넌트 1개 기준
>
> | 페이지 | gzip | brotli | 예산 대비 |
> |---|---|---|---|
> | `/` (방) | **94.4 KB** | 81.5 KB | 94.4% 사용 |
> | `/books/[slug]` (책) | **94.2 KB** | 81.3 KB | 94.2% 사용 |
>
> **폴리필 38.7 KB는 위 수치에서 제외했다.** Next.js가 폴리필 청크에 `nomodule` 속성을 붙이므로
> ES 모듈을 지원하는 브라우저는 이 파일을 내려받지 않는다. 대상 브라우저(최신 2개 버전 + iOS
> Safari)는 모두 여기 해당한다. 구형 브라우저까지 포함한 최악의 경우는 gzip 133.1 KB다.
>
> **측정 방법**: `next build`의 First Load JS 보고값이 아니라, 생성된 HTML이 실제로 참조하는
> 스크립트 파일을 모두 찾아 `nomodule`을 제외하고 gzip·brotli로 압축해 합산했다. Next.js의
> 보고값(96.5 kB)은 폴리필을 빼고 자체 압축한 근사치라 헌장의 "compressed" 기준과 정확히
> 일치하지 않는다.
>
> **판정**: 헌장 원칙 III을 **개정하지 않는다.** 예산 안에 들어왔다.
>
> **다만 남은 여유가 5.6KB이고, 이 시점에 실제 기능은 하나도 없다.** 방·책장·책등·책 창·보기
> 모드 전환·링크 가로채기가 전부 이 5.6KB 안에 들어가야 한다. 서버 컴포넌트는 JS를 늘리지
> 않으므로 화면 대부분은 무료지만, 클라이언트 컴포넌트는 아껴 써야 한다. 구현 중 예산을 넘기면
> 그때 다시 판단한다 — 이 실측값이 그 판단의 기준선이다.
>
> **관찰**: 94.4KB 중 대부분이 프레임워크 기저 비용이다(React + Next 런타임). Astro나 순수
> HTML을 택했다면 이 자리는 거의 비어 있었을 것이다. 유지보수 익숙함을 위해 지불한 비용이
> 얼마인지가 이제 숫자로 드러났다.

**Decision**: 예산 안에 들어왔으므로 헌장을 그대로 유지한다. 이 수치를 Lighthouse CI 예산으로
고정해(T016) 회귀를 막는다.

**Rationale**: Next.js App Router는 페이지에 아무것도 없어도 공유 런타임을 내려보낸다. 대략 90~110KB
수준으로 알려져 있으나 버전·설정·클라이언트 컴포넌트 수에 따라 달라지므로, 추측한 숫자로 헌장을 미리
완화하는 것은 검증 없이 기준을 낮추는 일이다. 헌장 스스로 예산 완화를 MAJOR 개정으로 규정한 이유가
여기에 있다.

**측정 방법**: `next build` 출력의 First Load JS와, 실제 `.next` 산출물의 gzip/brotli 압축 크기를 함께
기록한다. 대상 페이지는 방(`/`)과 책 단독 페이지(`/books/[slug]`) 둘 다.

**판정 기준**:
- 100KB 이하 → 헌장 그대로 유지, 예산을 CI 게이트로 고정한다.
- 초과 → 다음 순서로 대응한다. (1) 클라이언트 컴포넌트를 더 줄일 여지 확인,
  (2) 그래도 초과하면 실측값과 근거를 들고 **원칙 III의 MAJOR 개정 절차**를 밟는다.
  개정 없이 초과 상태로 진행하지 않는다.

**Alternatives considered**: 지금 예산을 175KB로 올려두는 안 — 검증 없이 기준을 느슨하게 만들고,
나중에 실제로는 예산 안에 들어왔을 경우 불필요하게 낮춘 기준만 남는다. 기각.

## R-2. 한 장씩 보기에서 장을 어떻게 나눌 것인가

**Decision**: **CSS 다단(column) + 스크롤 스냅**으로 브라우저가 나누게 한다. "전체 이어보기"는 같은
DOM에서 다단을 해제한 상태다. 즉 **두 모드는 같은 마크업에 CSS 클래스만 다르게 적용한 것**이다.

**Rationale**: 세 가지가 한 번에 풀린다.
1. 장 나눔 계산을 JS로 하지 않으므로 성능 예산(R-1)에 유리하다.
2. 창 크기가 바뀌면 브라우저가 알아서 다시 나눈다. 읽던 위치는 스크롤 위치로 유지되므로
   명세의 엣지 케이스("장 나눔 재계산 시 위치 손실")가 구조적으로 해소된다.
3. 낭독기와 키보드에는 두 모드가 **동일한 문서**로 보인다. 접근성 대안 경로를 따로 만들 필요가 없다.
   FR-011("전체 내용을 빠짐없이")도 자동으로 충족된다.

**측정 표시**: 현재 위치와 전체 분량(FR-010)은 스크롤 위치와 전체 너비의 비로 계산한다. 이 부분만
소량의 JS가 필요하다.

**Alternatives considered**:
- 콘텐츠에 장 구분자를 고정으로 박는 방식 — 구현은 단순하지만 화면 크기에 따라 빈 공간이 남거나
  넘치고, 320px에서는 대부분의 장이 잘린다. 기각.
- JS로 높이를 측정해 나누는 방식 — 정확하지만 리사이즈마다 재계산이 필요하고 코드가 커진다. 기각.

**남은 위험**: 다단 안에서 이미지나 표가 단 경계에 걸릴 때의 처리. 구현 시 `break-inside: avoid`로
대응하되, 프로필 책에는 큰 표가 없어 001에서는 위험이 낮다.

## R-3. 책 열기를 브라우저 방문 기록에 남길 것인가 (FR-012 딥링크)

**Decision**: **책마다 실제 정적 페이지 `/books/[slug]`를 만든다.** 방에서 책을 누르면 그 링크를
가로채 모달로 띄우고 `history.pushState`로 주소를 바꾼다. 뒤로 가기는 모달을 닫아 방으로 돌아온다.

**Rationale**: 헌장 원칙 I의 "JS가 실패해도 핵심 콘텐츠는 읽혀야 한다"를 그대로 만족한다. 책 링크는
평범한 `<a>`이므로 JS 없이 누르면 그냥 그 페이지로 이동한다. 검색 엔진도 각 책을 개별 문서로 수집한다.
공유받은 주소로 진입하면 정적 페이지가 바로 뜨므로 FR-012의 "추가 조작 없이 같은 책을 본다"가 성립한다.

**Alternatives considered**:
- 해시(`#book=slug`)만 쓰는 방식 — 페이지가 하나뿐이라 JS 없이는 아무것도 안 보이고 검색 수집도 안 된다. 기각.
- 모달을 방문 기록에 남기지 않는 방식 — 뒤로 가기를 누르면 사이트를 떠나게 되어 명세의 엣지 케이스에 걸린다. 기각.

## R-4. 폰트 전략

**Decision**: **한글 폰트 1종으로 줄이고, 실제 사용된 글자만 서브셋해 self-host한다.** 시안의 명조
계열 인상은 유지한다. 굵기는 본문용과 제목용 2종까지만 싣는다.

**Rationale**: 시안은 한글 폰트 3종(Gowun Batang, Nanum Myeongjo, Pretendard)을 외부 CDN에서
불러온다. 한글 폰트는 글리프가 많아 전체를 받으면 성능 예산을 지킬 수 없고, 헌장은 self-host와
서브셋을 요구한다.

**정적 사이트라서 가능한 것**: 콘텐츠가 전부 저장소 안에 있으므로, **빌드 시 실제로 쓰인 글자를 모아
그 글자만 담은 폰트를 생성**할 수 있다. 한국어 웹폰트에서 흔히 쓰는 유니코드 구간 분할보다 훨씬 작아진다.
`scripts/subset-fonts.mjs`가 이 일을 맡는다.

**주의**: 방명록(003)이 들어오면 방문자가 어떤 글자를 쓸지 미리 알 수 없으므로 이 전략을 그대로 쓸 수
없다. 003에서 방명록 영역만 유니코드 구간 분할 폰트나 시스템 폰트로 처리하는 방안을 다시 검토한다.

**Alternatives considered**:
- 시스템 폰트만 사용 — 용량 0이지만 시안의 인상을 완전히 잃는다. 기각.
- 유니코드 구간 분할(Google Fonts 방식)을 self-host로 재현 — 방명록까지 대응되지만 001에는 과하다.
  003에서 필요해지면 그때 도입한다.

## R-5. 모달 구현 방식

**Decision**: 네이티브 `<dialog>` 요소와 `showModal()`을 쓴다.

**Rationale**: 아래가 브라우저 기본 동작으로 제공된다. 직접 구현하면 코드가 커지고 접근성 결함이
생기기 쉬운 영역인데, 그 위험과 용량을 동시에 없앤다.

| 요구사항 | `<dialog>`가 주는가 |
|---|---|
| Esc 키로 닫기 (FR-005 일부) | ✓ 기본 제공 |
| 포커스 트랩 (FR-013) | ✓ `showModal()` 사용 시 |
| 배경 비활성화 (inert) | ✓ 기본 제공 |
| 열기 전 초점 복원 (FR-006) | ✓ 기본 제공 |
| 닫기 버튼 (FR-005 일부) | — 버튼만 두면 됨 |
| **바깥 영역 클릭으로 닫기 (FR-005 일부)** | **✗ 직접 구현해야 한다** |

**주의 — 바깥 클릭은 공짜가 아니다**: `<dialog>`의 `::backdrop`은 클릭 이벤트를 자체적으로 처리하지
않는다. FR-005는 "닫기 버튼, 바깥 영역 선택, Esc 키 중 어느 방법으로도" 닫히기를 요구하므로, 바깥
영역 클릭은 별도로 구현해야 한다. 다이얼로그 요소에서 발생한 클릭의 좌표가 내용 영역 밖인지 판정하는
방식이 일반적이다. 이 항목을 빠뜨리면 FR-005의 세 방법 중 하나가 조용히 누락된다.

**결과**: `design-notes.md`가 지적한 접근성 누락 3건 중 2건(Esc, 포커스 트랩)이 이 선택 하나로 해소된다.

**남은 1건**: `prefers-reduced-motion`(FR-016)은 CSS 미디어 쿼리로 별도 처리한다. 시안의
`bookPull`·`coverOpen` 애니메이션을 이 조건에서 제거한다.

**Alternatives considered**: 직접 만든 오버레이 + 포커스 트랩 라이브러리 — 브라우저가 공짜로 주는 것을
JS로 다시 만드는 셈이라 예산과 결함 위험 양쪽에서 불리하다. 기각.

## R-6. 좁은 화면의 책장 가로 스와이프

**Decision**: CSS 스크롤 스냅(`scroll-snap-type: x mandatory`)으로 구현하고, 책장으로 바로 가는 실제
링크 목록을 함께 둔다.

**Rationale**: 스와이프는 CSS만으로 되고 관성 스크롤도 브라우저가 처리한다. 문제는 키보드
사용자인데(FR-019), 링크를 함께 두면 Tab과 Enter만으로 이동할 수 있고 이는 낭독기 사용자에게도
목차 역할을 한다. 페이지 자체의 가로 스크롤이 아니라 컨테이너 내부 스크롤이므로 FR-017도 지킨다.

**Alternatives considered**: 터치 이벤트를 JS로 처리하는 스와이프 — 예산을 쓰고 관성·접근성을 직접
처리해야 한다. 기각.

## R-7. 디자인 토큰을 Tailwind와 어떻게 엮을 것인가

**Decision**: `src/styles/tokens.css`에 CSS 사용자 정의 속성으로 토큰을 정의하고, Tailwind 테마가 그
변수를 참조하게 한다. **임의값 클래스(`bg-[#ae1800]` 같은 형태)는 린트로 금지한다.**

**Rationale**: 헌장 원칙 V는 리터럴 값을 금지한다. Tailwind는 임의값 문법 때문에 리터럴이 스며들기
쉬운데, 린트로 막으면 규칙이 문서가 아니라 도구로 강제된다. 토큰 원본을 CSS 변수로 두면 라이트/다크
전환도 변수 재정의만으로 끝난다.

**토큰 출처**: `design-notes.md`에 정리된 책등 색 9종과 양피지·목재 색을 옮긴다. 이 값들은 이미 대비
계산으로 AA 통과가 확인되었으므로 그대로 쓴다.

**Alternatives considered**: Tailwind 설정에 색을 직접 적는 방식 — 다크 모드 전환과 런타임 테마
변경이 번거롭다. 기각.

## R-8. 검사 도구 구성

**Decision**:

| 대상 | 도구 | 게이트 |
|---|---|---|
| 콘텐츠 스키마·슬러그·모드 상태 로직 | Vitest | 실패 시 머지 차단 |
| 키보드 경로, 두 보기 모드, 딥링크 | Playwright | 실패 시 머지 차단 |
| 접근성 | axe-core (Playwright 통합) | 위반 0건 |
| 성능 예산 | Lighthouse CI | LCP·CLS·INP + JS 용량 |

**Rationale**: 헌장 원칙 IV가 요구하는 "위험을 따르는 테스트"에 맞춘다. 표현용 마크업의 스냅샷
테스트는 만들지 않는다 — 잘 깨지고 얻는 게 적다. 대신 접근성과 성능은 사람 리뷰 대신 도구가 매번 본다.

**Rationale (LHCI)**: 원칙 III의 숫자들이 문서에만 있으면 지켜지지 않는다. R-1의 실측값도 여기에
고정해 회귀를 막는다.

## R-9. 방문 기록을 어떻게 남길 것인가

**Decision**: **nginx 접근 로그를 기존 Loki/Grafana 스택으로 보낸다.** 클라이언트에 아무 스크립트도
내려보내지 않는다. Google Analytics는 채택하지 않는다.

**Rationale**: 세 가지 이유가 겹친다.

1. **헌장 개정이 필요 없다.** 기술·플랫폼 제약은 "방문자를 추적하는 서드파티 분석 도구나 임베드"를
   명시적 개정 없이 금지한다. 서버가 자기 접근 로그를 남기는 것은 서드파티 전송도 아니고 방문자
   브라우저에서 실행되는 추적도 아니다. 데이터가 본인 서버를 벗어나지 않는다.
2. **성능 예산에 영향이 0이다.** `gtag.js`는 압축 상태로도 50KB를 넘어, 100KB 예산을 실측하기도 전에
   초과시킬 뻔했다(R-1). 로그 방식은 클라이언트 비용이 없다.
3. **이미 구축되어 있다.** oneBite 클러스터의 `monitoring` 네임스페이스에 Loki·Grafana·Alloy가
   돌고 있고, Alloy는 DaemonSet으로 **모든 파드의 stdout을 k8s API로 읽어** namespace·pod·container·app
   라벨을 붙여 Loki로 보낸다. `portfolio` 네임스페이스에 nginx를 올리면 접근 로그가 자동으로 수집된다.
   추가 구축 작업이 없다.

**필요한 작업**: nginx 로그를 stdout으로 내보내고(기본 동작), 집계에 쓸 필드가 담기도록 로그 형식을
정한 뒤, Grafana에 대시보드를 하나 만든다.

**한계 (알고 선택한 것)**: 봇 트래픽 걸러내기와 재방문자 구분이 GA보다 거칠다. 세션·이탈률 같은
행태 지표는 얻기 어렵다. 개인 포트폴리오에서 실제로 궁금한 것은 "누가 언제 어떤 책을 봤는가"
수준이고, 이는 경로별 요청 수로 충분히 답할 수 있다고 판단했다.

**Alternatives considered**:
- **Google Analytics** — 기능은 가장 풍부하지만 헌장 개정 2건(서드파티 분석 허용 + 성능 예산 상향)이
  선행되어야 하고, 방문자 데이터가 구글로 넘어가며, 쿠키 고지 문제가 따라온다. 얻는 것에 비해 비용이 크다. 기각.
- **자체 호스팅 Umami/Plausible** — 쿠키가 없고 JS도 1~2KB라 헌장과 크게 충돌하지 않으며 경로별 지표가
  정확하다. 다만 컨테이너와 데이터베이스를 새로 운영해야 한다. 로그 방식으로 부족하다고 판단되면
  003에서 방명록 DB와 함께 도입하는 것을 재검토한다. 지금은 보류.
